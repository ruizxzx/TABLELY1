# Build 32 known issues and release gates

1. **Loyalty redemption and partial refunds:** Point redemption is not integrated into authoritative checkout/payment quotes; do not advertise redemption as available. The restaurant order/payment schema has no partial-refund workflow, so partial-refund loyalty reversals remain unimplemented. Signed-in customers can view a restaurant-scoped wallet/history and explicitly enroll or withdraw at `/customer/loyalty`. Apply `20261024063127_build32_loyalty_explicit_consent.sql` before enabling enrollment.
2. **Point-expiry deployment:** `20261024060000_build32_loyalty_expiry_processor.sql` and `POST /api/cron/loyalty-expiry` add bounded, idempotent expiry ledger processing. The migration is not applied automatically; configure a scheduled caller after staging migration validation. The wallet excludes expired earning entries before the scheduled processor records them.
3. **Feedback delivery:** Dynamic neutral survey questions, rating-independent Google review links, a separate checkout email-consent choice, and a bounded Resend worker are implemented. Apply `20261024064200_build32_feedback_email_delivery.sql` and configure the email worker and server secrets before enabling email delivery. Live email-provider testing and invitation-frequency controls remain outstanding.
4. **WhatsApp onboarding and reporting:** Order template variables now have a fixed documented order; STOP revokes service, marketing, and feedback WhatsApp consent and cancels queued messages. Webhook persistence errors are retried with non-2xx responses, and status updates are monotonic. Meta Embedded Signup, template-status import, verified phone ownership and usage/cost reporting remain outstanding.
5. **Google provider validation:** OAuth, synchronization and explicit reply publication are implemented but were not tested against an approved live Business Profile API project. Google API access and credentials are external prerequisites.
6. **Menu translations:** Customers can select English, Hindi or Bengali even when a restaurant has not manually enabled those languages. Dashboard → Menu prepares missing Hindi/Bengali translations into the existing translation tables using the branch's approved `menu_extraction` text route; both Dashboard → Menu and onboarding also provide a manual sync action that regenerates and saves all menu translations in bounded batches. The explicit full-sync action replaces existing saved translations, including manual edits, after each AI response validates. Customer language selection only reloads the saved public menu and never calls AI. Text edits invalidate only the corresponding Hindi/Bengali rows, which Dashboard → Menu regenerates when loaded. Apply the Build 28.6 AI-management migration, `20261024140000_build32_public_variant_translations.sql`, and `20261025010100_build32_refresh_menu_translations.sql`, then configure an approved text model/route before translation generation is available. Provider usage, budgets and failures are handled by the central AI router; live provider generation was not verified.
7. **Metrics and anonymous contacts:** Engagement metrics use exact branch-scoped database aggregates; anonymous preference records are normalized and uniquely keyed by organization and phone. The new hardening migration must be applied before relying on these changes in a database.
8. **Regression testing:** Automated contract checks cover the remediated paths, but do not replace database-backed tenant/RLS tests, real provider webhooks or browser flows.
9. **Migration/deployment gates:** Additive migrations include `20261024070000_build32_metrics_language_phone_hardening.sql`, `20261024140000_build32_public_variant_translations.sql`, and `20261025010100_build32_refresh_menu_translations.sql`. Historical duplicate/invalid migration filenames still prevent repository migration preflight. No staging project was verified or migrated during this change; reconcile the migration ledger without renaming applied migrations, then apply and validate pending migrations on staging.
10. **External validation:** Live Meta/Google/Resend credentials and a staging browser environment were not supplied. Real provider and browser tests remain release gates.
11. **Existing tooling/security findings:** ESLint fails during configuration loading before source linting. `public.rate_limit_buckets` still has RLS disabled; review and add suitable policies before enabling RLS.
12. **Restaurant workspace creation:** `20261024130000_fix_restaurant_workspace_creation.sql` restores the OWNER capability flags required by the staff constraint and retains default menu-category seeding. Apply this additive migration to the target database before retrying restaurant onboarding; live database migration history was not available for verification.
13. **Onboarding menu flow:** Menu categories and items can be added directly in onboarding, and saved menu items update the menu-step completion status. AI file/photo import now uses the existing secured parse, review and commit APIs; selected imports remain inactive drafts until restaurant staff review and activate them. Successful commits refresh the branch menu and mark the onboarding step saved. Onboarding includes a manual Hindi/Bengali translation sync for the saved branch menu. Photo extraction requires an approved vision-capable `menu_extraction` route. The wizard has a previous-step control; menu setup can be explicitly skipped and resumed before launch. Existing menu data is checked branch-scoped when the menu/review step loads.
